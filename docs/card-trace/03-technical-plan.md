# 《牌局档案》技术方案

版本：1.0 · 更新日期：2026-09-24 · 状态：开发前设计，尚未实现业务功能

## 1. 用户硬要求与技术基线

- **最低支持 iOS 14.0**，覆盖 Debug 与 Release；不得为使用新 API 提高最低版本。
- **暂不引入付费**，不实现内购、订阅、StoreKit 业务或付费墙。以上两项为用户硬要求。
- 当前技术基线：Swift，沿用工程 Swift 5 语言模式；UIKit＋Auto Layout，面向 iPhone 竖屏。首版不安排广告变现，章节按游戏进度解锁。
- 核心游玩、关卡、提示、复盘与存档全部离线运行；无账户、服务器及第三方依赖。
- 保持 Bundle ID、签名团队和发布配置不变。本次仅整理方案，未修改工程代码或配置。

原方案中的“提高至 iOS 15”“StoreKit 2 解锁”“免费试玩后购买章节”全部作废。后续如变更商业模式，应重新评审，不作为首版隐藏需求。

## 2. 架构与模块边界

使用轻量分层，不为四个页面引入复杂框架。规则核心独立于 UIKit，界面和关卡制作工具复用同一套规则。

| 层级 | 主要对象 | 职责 |
|---|---|---|
| 展示层 | 各页面 ViewController、CardView、CollectionViewCell | 呈现状态，接收操作，执行动画和无障碍反馈 |
| 交互状态层 | GameSession、GameAction、UndoHistory | 管理摆牌、选牌、笔记、撤销、提交与恢复 |
| 规则核心 | RuleEngine、ConstraintEvaluator、ReplayBuilder | 计算合法出牌、赢家、顺序与证据矛盾；输出结构化结果 |
| 数据层 | LevelRepository、SaveRepository、Settings | 读取内置关卡，迁移与保存进度，管理偏好 |
| 作者工具 | LevelValidator、SolutionCounter | 制作阶段检查结构、可解性、唯一性及提示一致性 |

数据流为“用户操作 → GameAction → 新状态 → 校验结果 → 界面”。卡牌视图不持有独立游戏事实；复盘动画消费规则引擎产生的事件列表，不自行重新计算赢家。界面刷新在主线程，存档和有限校验使用 DispatchQueue；同一局状态修改串行执行。

## 3. 规则、证据与玩家状态

必须区分六类数据：

1. **规则定义**：牌组、座次、首轮领出者、必须跟花色、同花色比较方式，以及是否有王牌。首版教学规则固定为无王牌。
2. **公开事实**：明确可信的已知牌、座次、已发生的动作。
3. **证词**：来源、显示文本及可计算的约束表达式。证词不默认等同事实；存在错误证词的关卡必须公开“恰好有几条错误记录”。
4. **玩家假设**：拖入的位置、对证词的判断、笔记。假设可以暂时矛盾，但不能破坏牌的唯一性等数据结构约束。
5. **作者答案**：标准完整分配、证词真假与解释，仅用于关卡验证、结算和明确请求的揭晓。
6. **提示步骤**：从公开信息推导出的结论及所依赖的证据，用于分层提示。

局内以稳定的 CardID 标识每张牌。每张牌只有一个权威位置：牌池，或“轮次＋玩家”对应的位置。移动命令同时清空旧位置并写入新位置；目标已有玩家放置的牌时执行交换，从牌池拖入时原牌回到牌池，不能静默覆盖。目标为固定公开牌时拒绝操作，锁定的公开牌不可移动。

“玩家在每轮出了什么牌”是可编辑数据，“实际行动顺序和赢家”是派生数据。固定座次和领出者确定顺序；领出花色中最大的牌获胜，赢家领出下一轮。上一轮尚不能确定赢家时，下一轮顺序保持待定，避免界面暗示未证明的信息。

## 4. 关卡 JSON 与版本

关卡通过 Bundle 内 JSON＋Codable 加载。`schemaVersion` 表示结构版本，`contentRevision` 表示同一关卡的内容修订；`id` 发布后保持稳定。牌数、重复 ID、引用、轮次数及规则版本都须在加载时检查。

下例仅展示数据结构，缺少完整证词、提示和答案，不是可发布关卡：

```json
{
  "schemaVersion": 1,
  "contentRevision": 1,
  "id": "chapter01.level01",
  "chapterID": "chapter01",
  "rules": {
    "id": "follow_suit_no_trump",
    "version": 1,
    "players": ["A", "B", "C"],
    "firstLeader": "A",
    "roundCount": 2
  },
  "cards": ["S2", "S5", "S9", "H3", "H7", "H10"],
  "facts": [
    {"kind": "cardPlayed", "round": 1, "player": "A", "card": "S5"}
  ],
  "testimonyPolicy": {"falseCount": 0},
  "testimonies": [
    {
      "id": "t1",
      "text": "第一轮 B 获胜。",
      "constraint": {"kind": "roundWinner", "round": 1, "player": "B"}
    }
  ],
  "hints": [],
  "authorSolution": {"plays": [], "falseTestimonyIDs": []}
}
```

约束使用受支持的枚举与字段，禁止执行 JSON 携带的脚本。自然语言证词与机器约束分开存储，制作时人工核对含义。旧关卡修订导致摆牌位置不再兼容时，只重置该局草稿并说明原因，保留已完成记录。

## 5. 校验、提示和唯一解

局部校验采用三态：

| 结果 | 含义 | 界面反馈 |
|---|---|---|
| 矛盾 | 已有信息足以证明违反规则或可靠约束 | 指明相关牌位和证据，解释首次可证明的冲突 |
| 待推断 | 信息不足，当前无法证明或否定 | 保持中性，不显示为正确 |
| 当前成立 | 对该条约束的必要信息完整且检查通过 | 标记该约束成立，不代表全局答案正确 |

有错误证词的题目按公开的错误数量联合判断，不能因为某一证词不成立就立即判错。提交完整答案时，执行全部规则、事实、证词数量和任务目标检查；若发现另一个合法解，应视为关卡质量问题，不强制玩家匹配作者摆法。

日常反馈不能逐格与标准答案比较并亮红绿灯。提示按“指出相关证据 → 解释推理方向 → 给出一个有依据的结论”分层展开；明确揭晓操作另设确认，避免误触损失解谜过程。

作者工具使用回溯求解：先应用已知牌与手牌容量约束，选择候选最少的位置，逐步检查跟花色、赢家轮转及证词约束进行剪枝。找到第二个不同解即判定非唯一；超时只能标为未验证。检查应覆盖完整牌序、手牌归属，以及题目要求回答的证词判断。发版内容必须全部完成结构、唯一解、提示与解释核对。

手机只需执行当前假设的局部检查与回放。更深搜索若有必要，应有时间预算、取消能力及陈旧结果丢弃机制，不能阻塞拖拽。

## 6. 存档与撤销恢复

进度与草稿保存到 Application Support，使用版本化 Codable 文件和原子替换；串行写入，保留一份最近可用备份。保存内容包含 `saveVersion`、关卡 ID／修订号、摆牌、笔记、已用提示、完成记录及有界撤销栈。UserDefaults 仅保存音效、触感、字体等简单设置。

每次完整操作生成可撤销命令；撤销恢复操作前的整份必要状态，再重新派生赢家与校验结果。首版不实现独立重做入口或重做历史。复盘位置和动画中间帧不写成游戏事实。正常操作后短暂合并写入，完成关卡、退出关卡和进入后台时触发保存；不能仅依赖后台回调，因为系统可能提前终止进程。

读取流程为校验 → 必要迁移 → 恢复 → 重算派生数据。迁移按版本逐步执行并保留原始备份；损坏文件优先回退备份，失败后提供重置当前草稿的入口。遇到未知更高版本时不直接覆盖原文件。首版不承诺跨设备同步。

## 7. UIKit 落地与 iOS 14 兼容

原型 PNG 是视觉和布局参考，**不可将整屏图片作为可交互 UI**。扑克牌的点数、花色、选中态和证据标记由真实控件或图层绘制；插画、纸张纹理作为 UIImage 资源，放入 Asset Catalog 并控制解码尺寸。

牌池和出牌区域使用 UICollectionView、自定义 Cell 与 Auto Layout。使用 UICollectionViewDragDelegate／DropDelegate 处理应用内拖放，拖动项携带 CardID；同时提供“点牌 → 点目标位置”、移回牌池和 VoiceOver 自定义操作。手势取消时不提交状态，动画结束不承担写入业务数据的职责。

| 需求 | iOS 14 基线 |
|---|---|
| 按钮样式 | UIButton 的标题、背景、Insets 与图层；不使用 iOS 15 的 UIButton.Configuration |
| 列表更新 | 常规数据源、reloadItems／performBatchUpdates；不使用 iOS 15 的 reconfigureItems |
| 状态管理 | 普通 Swift 类型与显式状态回调，不引入 Observation 或 SwiftData |
| 异步工作 | DispatchQueue 和串行队列作为基线，不依赖较新并发 API |
| 布局与导航 | UIKit、Safe Area、Auto Layout；不依赖新系统专属组件 |

交付前逐项检查 API availability，不能只因最新模拟器可运行就认为兼容 iOS 14。小屏上按轮次纵向滚动，线索可折叠，主要操作保持可触达；不通过缩小全屏造成牌面难辨。提供足够触控区域、Dynamic Type、VoiceOver 牌名与位置描述，花色形状和文字共同表达信息；尊重“减弱动态效果”，动画可跳过。

## 8. 实施与验收

先以 **8 关可玩原型** 为目标：规则核心 → 摆牌与撤销 → 校验与回放 → 本地恢复 → 四屏视觉与教学。确认目标用户能理解推理后，再按 40 关的首版目标扩充内容及章节进度解锁；数量可根据测试调整。每日内容和残局实验室留作后续评审，不进入首版必交范围。

验收至少覆盖：

- **规则**：跟花色、缺门、同花色比较、领出者轮转、错误证词数量、无解与多解识别。
- **状态**：移动／交换／取消拖拽不丢牌不重复；撤销、退出重进、存档迁移与损坏恢复一致。
- **产品**：8 关闭环，再验证全部正式关；提示可推导、不意外泄题，首版无付费入口和联网前置条件。
- **构建与设备**：Debug／Release 编译检查与有效 Target 最低版本检查；实际 iOS 14 设备或兼容环境、较新系统、小屏及无障碍体验分别验证。新 SDK 编译成功不等于旧系统实测通过。

主要风险是关卡设计和提示质量、求解空间增长、小屏时间线拥挤，以及旧系统运行差异。采用小牌组先行、作者工具验证、有界计算和早期真机验收控制这些风险。开发周期取决于 8 关验证结果，不能把美术原型完成等同于玩法完成。
